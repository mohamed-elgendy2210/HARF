# Security Controls and Open Risks

## Implemented controls

- Registration accepts only strict `parent` and `specialist` request shapes. Role, approval, account status, subscription, and permission fields supplied by a client are rejected rather than mass-assigned.
- Passwords are hashed with Node.js `scrypt` using a random 16-byte salt and a 64-byte derived key. Login uses a dummy scrypt operation for unknown users and constant-time key comparison.
- Session identifiers and email verification/password reset tokens are cryptographically random. Only SHA-256 digests of session/auth tokens are persisted. Session and auth-token expiration is checked in queries and again in service logic; TTL indexes are cleanup aids.
- Session cookies are HttpOnly and SameSite=Lax, Secure in production, and use the `__Host-` prefix in production. Authenticated state-changing requests require the session-bound CSRF header and exact configured Origin.
- Login, registration, verification/resend, and password-recovery endpoints have rate limits. Account APIs fail closed with 503 when MongoDB is unavailable.
- Email verification and recovery links are single-use and purpose-scoped. Password reset revokes all existing sessions and auth tokens. Rejection or suspension revokes sessions, preventing old sessions from becoming active after later re-approval/reactivation.
- Admin endpoints require a session, verified active account, admin role, and CSRF token. Admin account writes are limited to parent/specialist records. Game-library mutations accept only strict schemas, record audit events, and cannot set publication state/version or storage paths from client input. Admin bootstrap is CLI-only and a MongoDB partial unique index enforces one admin under the current first-admin bootstrap policy.
- Specialist self-service updates operate only on the authenticated account. The public directory filters for verified, approved, active specialists with a complete profile and explicit public-listing consent; it omits email addresses.
- Specialist registration requires a signature-checked personal photo and both sides of the professional card. Images are limited to PNG/JPEG/WebP at 5 MiB each, stored with generated names outside the application tree and restrictive filesystem permissions where supported. Only approved, verified specialists with a complete name/profile, public-listing consent, and all required verification images are eligible for the public directory; malformed names made only of punctuation are not considered complete. Only the approved public-directory endpoint serves the portrait; verification documents are served only through an administrator-authorized, audited, private/no-store route. Account serializers expose completion booleans only, never storage names or verification images.
- Parent-child APIs require a verified, approved, active parent and scope child reads/updates/consent operations to both the requested child ID and the authenticated parent ID. A mismatched owner receives the same 404 as an unknown child. Request schemas reject owner IDs and all fields outside the profile, status, or consent contract.
- Parent game content and answer checks require a verified, approved parent, an active time-bounded subscription, and an activity included in the configured learning path. Parent answer requests require the selected owned child ID, a submission ID, and session-bound CSRF validation; the API returns correctness without answer-key indexes and stores short-lived answer receipts. Parent attempts require a complete set of server-recorded receipts and are scored from those records, not from client-submitted answers. Only administrator-selected trial games are public and trial gameplay is not persisted.
- Administrator account creation and deletion are limited to authenticated, approved admins with CSRF validation and audit records. Admin deletion cannot target the active administrator or the final administrator; deleting an admin revokes their sessions and auth tokens.
- Parent attempt writes and learning-progress reads verify the active subscription and child ownership. Attempt persistence and path progress also require an active child and current learning-data consent. A separate owner-scoped progress record stores earned milestones; prior attempts and milestones are retained.
- Subscription periods can only be created through the authenticated administrator's manual-payment review after the parent account is verified, approved, and active. Price, currency, payment instructions, and transfer reference are snapshotted at request/subscription creation; receipt upload alone never creates an entitlement. The public trial remains outside subscription enforcement.
- Parent payment requests and receipts are scoped to the owning parent. Administrator settings, payment queue, review, and receipt routes require an active verified administrator and CSRF. Receipt downloads use private, no-store responses; uploads accept signature-checked PNG/JPEG/WebP/PDF only, up to 5 MiB, and use generated names in private storage.
- Payment request uploads are rate-limited to 10 requests per 15 minutes per client IP before multipart parsing.
- Specialist schedule APIs require the authenticated, verified, approved, active specialist account; a specialist can edit only their own schedule. Public availability is returned only for complete, explicitly listed, approved specialists.
- Appointment requests require an authenticated approved parent, an active child scoped to that parent, and a currently offered slot from an approved specialist. Appointment list/detail reads are owner-scoped to the requesting parent or assigned specialist; unrelated families/specialists and administrators cannot access them.
- Decision writes are assigned-specialist-only and atomically compare pending state plus a future decision deadline. A unique partial MongoDB multikey index reserves every 15-minute interval of an appointment, preventing overlapping concurrent bookings. Reject/expire releases the reservation; a worker checks for expiry every minute and request/list paths also expire overdue pending records before returning them.
- Appointment request submissions are rate-limited to 10 per 15 minutes per client IP. Appointment records contain only the authorized child display name when serialized and no medical history. Booking does not check or change subscription entitlement.
- Session start/completion writes are assigned-specialist-only, require CSRF, require an accepted booking, and transition atomically with server-side timestamps. Private specialist notes and parent-visible educational reports are separate fields; parent serializers explicitly omit private notes. Admin accounts cannot access participant appointment/session or join routes. Completion audits contain appointment identity and timestamps only, not report or note text.
- Video-access requests are POSTs protected by authentication, approved-account, participant-role, CSRF, and per-IP rate limiting. Every request re-queries the appointment scoped to the current parent or assigned specialist, checks confirmed status and server-side joining times, and returns only the Jitsi domain and opaque room details with `Cache-Control: private, no-store`. Room names are 256-bit random values stored on the appointment and excluded from public/list serializers. The default public Jitsi service does not authenticate Haraf participants or guarantee participant-only access; a self-hosted/authenticated deployment and verified server-side JWT/moderator controls are required for that assurance. No recording/transcription is enabled.
- Admin appointment monitoring, provisioning retries, and video-test history/creation/results are restricted by the server's existing active-admin, role, and CSRF middleware. Monitoring is paginated and omits room credentials. Retry requires a confirmed future booking with no room, conditionally associates a single room, and audits both success and failure. Independent video tests are rate-limited per administrator and IP; test room identifiers are cryptographically random, second-participant tokens are one-use SHA-256 digests with bounded expiry, and test records contain no appointment/family relation or media. The second-participant endpoint still requires an administrator session and CSRF. These application checks cannot prevent a person who learns the room name from joining a public Jitsi room.
- Learning-path writes are administrator-only, validated against published non-trial game IDs, duplicate IDs and bounded progression parameters. Progression recommendations use the configured sample of recent attempts and are presented as educational suggestions rather than diagnoses.
- Child profiles retain only a short display name and optional broad age band; parent ID is server-assigned and omitted from API responses. Profiles are archived rather than hard-deleted in Phase 3.
- Consent is stored as append-only child-scoped grant/withdraw history and defaults to not granted. Game attempts/progress and appointment report creation/parent reads check current consent. `harf-child-data-v1` is a schema marker, not a reviewed legal consent policy.
- Sensitive administrative and account lifecycle actions create minimal audit events. Logs omit query strings and redact sensitive fields; centralized errors do not expose stack traces.
- Admin report JSON and CSV routes share the verified/approved administrator router. Date filters are schema-validated and capped at 366 days. Learning summaries contain aggregate counts only; payment totals count revenue only for manually approved requests, never for a submitted receipt.
- Notification list/read APIs derive the recipient exclusively from the authenticated session and include that recipient in every database filter. Responses exclude the internal recipient ID. Notification email is generic, optional, and best-effort; SMTP errors are logged without reversing committed actions.
- Production non-health API requests require recognized HTTPS. Proxy trust is disabled by default and must be configured for the actual deployment path.
- Media uploads require administrator authorization, Origin/CSRF checks, a per-IP in-memory rate limit, a single multipart file and a 10 MB multipart cap. Detected file signatures—not browser MIME/extensions—determine accepted formats. Per-kind limits are 5 MB images, 10 MB audio and 3 MB animation.
- Media is stored under generated UUID names outside the application tree, not served as static files. Public delivery requires an active asset referenced by a published game, and uses `nosniff`, sandbox CSP, and no-store headers. SVG is rejected; Lottie JSON is bounded and expressions/external references are rejected. The current player does not execute or render uploaded Lottie JSON.
- Local HTTP is for synthetic development data only; never submit real credentials or private child, payment, or consultation information over unencrypted HTTP.

See [Phase 9 completion](./phase-9-completion.md) and [Phase 10 completion](./phase-10-completion.md) for reporting/notification and consultation checks and limitations.

## Known risks and deployment work

- **Rate-limit distribution:** `express-rate-limit` uses its default in-memory store. Limits do not coordinate across instances and reset on process restart. A shared store is required before horizontal scaling.
- **Real database operations:** The API tests use in-memory repositories. Live MongoDB connection, startup index creation, cross-process consistency, and production database concurrency must be verified in the deployment environment.
- **Email delivery:** No SMTP provider or credentials were configured. Delivery, bounce handling, sender reputation, provider TLS, and reset-email timing have not been verified.
- **Session rotation:** Sessions are opaque bearer credentials. A production deployment still needs operational policies for session lifetime/revocation, account recovery, alerting, and incident response.
- **Cross-site deployments:** The current SameSite=Lax cookie policy supports same-site frontend/API deployment; a cross-site deployment will need explicit browser cookie-policy evaluation and likely a coordinated secure cookie change.
- **Admin lifecycle:** The initial bootstrap CLI intentionally permits only one administrator. Additional administrator provisioning/rotation, MFA, and a break-glass recovery procedure are not implemented. Run the bootstrap command only once, from a trusted interactive terminal.
- **Child privacy and retention:** Child profiles and consent history are implemented, but no production retention/deletion process or jurisdiction-reviewed consent policy exists. Do not use the current schema marker as legal consent wording. Define those policies before accepting real child data.
- **Specialist verification images:** Professional-card images are stored outside the application tree with restrictive file permissions, but are not encrypted by the application. Retention and deletion periods, access-review procedure, and jurisdiction-specific handling of professional identity documents remain unresolved and must be decided before production use.
- **MongoDB compatibility:** Learning progress aggregation uses MongoDB `$topN`; deploy MongoDB 5.2 or newer and verify it against the actual managed/self-hosted server version.
- **Payments and subscriptions:** Payment is manual. An administrator must verify a transfer outside Harf; the app does not connect to Vodafone Cash/InstaPay or automatically verify a receipt. Review creation/finalization is idempotency-aware but not transactionally atomic across MongoDB collections; a temporary database failure can leave a newly created subscription awaiting payment-request finalization. Retrying review recovers via the unique payment link, but this workflow needs MongoDB-backed failure-injection testing. No cancellation, refund, pending-request expiry, auto-renewal, or receipt-retention/deletion policy is implemented. Receipt storage is local filesystem storage and needs production access controls, backup, durability, and retention decisions.
- **Learning-rule validity:** Thresholds and ordering are configurable, but have not been evaluated by educational or speech-language professionals. They are intentionally transparent and non-diagnostic. Product review is required before representing them as evidence-based.
- **Video privacy/access control:** Public Jitsi room names are high entropy but not an access-control mechanism; anyone who obtains the room name may be able to join. Complete a child-data/provider review and configure authenticated Jitsi before confidential production use. Provider connectivity and real-browser permission behavior were not exercised in this test environment.
- **Media storage operations:** Files are stored on local disk. Production durability, access controls, backups/restore, capacity, and cross-node shared storage remain deployment work. Historical versions can keep assets undeletable until a retention policy is approved.
- **Appointments and consultations:** Server-side ownership and slot consistency are implemented, including MongoDB unique indexes for reservations and room names. A live MongoDB concurrency smoke check was run locally, but production replica-set failover/load behavior is not verified. Local per-IP rate limits are not shared across instances. No appointment cancellation, rescheduling, lateness, no-show, refund, or payment collection workflow exists; determine policies before production booking. The public Jitsi provider has no participant-only access guarantee.
- **Other product security:** Audit retention/access policies are not implemented or reviewed. Provider-specific privacy/security requirements cannot be evaluated until a provider is selected. SMTP notification delivery is best-effort and must be operationally monitored.
- **Production configuration:** Validate TLS termination, trusted proxy addresses, HTTPS origins, MongoDB network controls/backups, email secrets, deployment secrets, and monitoring against the actual hosting topology.

No production credentials, real user data, or SMTP secrets are present in `.env.example`.
