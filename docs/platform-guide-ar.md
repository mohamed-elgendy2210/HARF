# دليل منصة حرف (Harf)

هذا الدليل يشرح مكونات المنصة، الأدوار والرحلات الأساسية، طريقة التشغيل، وكيفية تشخيص الأخطاء المتكررة. يصف السلوك الموجود في المستودع، وليس نظامًا منشورًا أو إعدادًا إنتاجيًا جاهزًا. عند اختلاف السلوك الفعلي عن هذا الدليل، اعتمد على إعدادات البيئة والسجلات والاختبارات الحالية.

## 1. نظرة عامة

حرف منصة عربية RTL لممارسة مهارات اللغة والتواصل لدى الأطفال من خلال ألعاب تعليمية. يمكن لولي الأمر إدارة ملفات الأطفال ومتابعة مسارات التعلم، ويمكن للأخصائي إدارة المواعيد والجلسات المصرح بها. يقدم المشرف أدوات مراجعة الحسابات والمحتوى والمدفوعات وإعدادات المنصة.

### المكونات التقنية

| المكوّن | التقنية | المسؤولية |
|---|---|---|
| واجهة المستخدم | React 19 وVite 7 | الموقع العام ولوحات ولي الأمر والأخصائي والمشرف والألعاب |
| واجهة الخادم | Express 5 وNode.js | REST API، التحقق من الصلاحيات، تنفيذ قواعد العمل، وإرجاع الأخطاء |
| قاعدة البيانات | MongoDB وMongoose | الحسابات، الجلسات، الأطفال والموافقات، الألعاب، المسارات، الاشتراكات، المدفوعات والمواعيد |
| الملفات | تخزين خاص خارج مجلد المشروع | صور وأصوات الألعاب، مستندات التحقق، وإيصالات الدفع |
| البريد | SMTP اختياري محليًا ومطلوب في الإنتاج | التحقق من البريد واستعادة كلمة المرور والتنبيهات البريدية |

تبدأ مسارات API من `/api/v1`. في التطوير يمرر Vite طلبات `/api` إلى الخادم، لذلك لا تحتاج الواجهة عادةً إلى عنوان API مستقل. التفاصيل المعمارية الكاملة موجودة في [وثيقة المعمارية](./architecture.md)، والإعداد الإنتاجي في [وثيقة النشر](./deployment.md).

## 2. الأدوار والوظائف

### الزائر

- مشاهدة الصفحة العامة ودليل الأخصائيين الذين وافقوا على الظهور.
- تجربة الألعاب المجانية التي يحددها المشرف (حتى أربع ألعاب منشورة).
- إجابات التجربة مؤقتة ولا تُحفظ كحساب أو سجل طفل.

### ولي الأمر

- التسجيل والتحقق من البريد، ثم انتظار موافقة المشرف عند الحاجة.
- إنشاء ملفات أطفال محدودة البيانات وإدارتها وأرشفتها وإعادة تفعيلها.
- إدارة موافقات البيانات على مستوى كل طفل. لا تُمنح الموافقة تلقائيًا.
- استعراض توصيات ومسارات تعليمية قابلة للتفسير، ثم تأكيد المسار المقترح.
- استخدام الألعاب المدفوعة عند وجود اشتراك نشط وموافقة بيانات سارية.
- تقديم طلب دفع يدوي ومتابعة حالته؛ رفع الإيصال وحده لا يفعّل الاشتراك.
- طلب موعد اختياري ومشاهدة سجل المواعيد والتقارير التعليمية المصرح بها.

### الأخصائي

- التسجيل والتحقق من البريد وانتظار موافقة المشرف.
- إدارة الملف المهني ومواعيد التوفر وطلبات الحجز الموجهة إليه.
- قبول أو رفض الطلبات، ثم تسجيل بدء الجلسة وإتمامها.
- كتابة ملاحظات خاصة منفصلة عن التقرير التعليمي الذي قد يراه ولي الأمر.
- لا يمكنه الاطلاع إلا على بيانات الأطفال المرتبطة بمواعيد مصرح بها معه.

### المشرف

- مراجعة حسابات أولياء الأمور والأخصائيين وإدارة حسابات المشرفين وفق قيود النظام.
- إدارة مسودات الألعاب ووسائطها ونشر نسخ ثابتة واختيار ألعاب التجربة.
- إدارة مسارات التعلم والاستبيان وإعدادات الاشتراك ومراجعة طلبات الدفع.
- مشاهدة تقارير إجمالية وتصدير CSV وإدارة الإشعارات والإعدادات المتاحة.
- إنشاء أول حساب مشرف يتم من سطر الأوامر، وليس من مسار تسجيل عام.

## 3. الرحلات الأساسية وقواعد العمل

### الحساب والدخول

1. يسجل المستخدم كولي أمر أو أخصائي.
2. يرسل النظام رسالة تحقق بالبريد؛ لذلك تتطلب تجربة التسجيل والاستعادة إعداد SMTP صالحًا.
3. يراجع المشرف الحسابات التي تتطلب موافقته.
4. بعد التحقق والموافقة وتفعيل الحساب، يمكن للمستخدم دخول المسارات المسموح بها لدوره.

الجلسة تحفظ في Cookie من نوع HttpOnly، وتصبح Secure في الإنتاج. الطلبات التي تغيّر البيانات تتطلب رمز CSRF وأصلًا موثوقًا. لا تُعامل حماية الواجهة على أنها بديل عن صلاحيات الخادم.

### الأطفال والتعلم والألعاب

- كل قراءة أو تعديل لملف طفل يتحقق في الخادم من هوية ولي الأمر وملكية الطفل.
- الوصول إلى سجل المحاولات والتقدم يتطلب طفلًا نشطًا وموافقة بيانات سارية، كما تتطلب الألعاب المدفوعة اشتراكًا نشطًا.
- التوصيات تعليمية وليست تشخيصًا طبيًا. لا ينشئ النظام مسارًا للطفل تلقائيًا؛ ولي الأمر يراجع التوصيات ويؤكد ما يناسبه.
- تُحسب نتيجة المحاولة من بيانات يتحقق منها الخادم، لا من نتيجة يرسلها العميل وحدها.
- الألعاب العامة التجريبية لا تتطلب حسابًا ولا تحفظ إجاباتها.

### الاشتراكات والمدفوعات

- يحدد المشرف السعر وتعليمات وسائل الدفع اليدوي المتاحة.
- يرسل ولي الأمر طلبًا مع مرجع التحويل وإيصال اختياري.
- يراجع المشرف الطلب ويقبله أو يرفضه. لا ينشأ الاشتراك إلا بعد المراجعة والقبول.
- رسوم المواعيد منفصلة عن الاشتراك، ولا يلزم الاشتراك لحجز موعد.

### المواعيد والاستشارات

- يحدد الأخصائي مواعيده المتاحة، ويحجز ولي الأمر موعدًا لطفل يملكه.
- يمنع الخادم الحجز المتداخل، وتنتهي الطلبات المعلقة بعد 48 ساعة مع تحرير الفترة.
- يمكن للأخصائي بدء الجلسة وإتمامها وكتابة ملاحظات خاصة وتقرير تعليمي منفصل.
- تكامل الفيديو غير مفعّل؛ طلب الوصول إليه يفشل مغلقًا برسالة `VIDEO_PROVIDER_NOT_CONFIGURED`.

## 4. التشغيل المحلي

### المتطلبات

- Node.js إصدار 22.12 أو أحدث وnpm إصدار 10 أو أحدث.
- MongoDB للوظائف المعتمدة على البيانات. يمكن تشغيل الصفحة العامة بدونه، لكن جاهزية API ومسارات البيانات لن تكون متاحة.
- SMTP تجريبي لتجربة التحقق من البريد واستعادة كلمة المرور.

### خطوات التشغيل على Windows PowerShell

من مجلد المشروع:

```powershell
Copy-Item .env.example .env
npm install
npm run dev
```

عدّل `.env` محليًا فقط، ولا تضف أسرارًا حقيقية إلى المستودع. لتشغيل MongoDB محليًا اضبط مثلًا:

```text
MONGODB_URI=mongodb://127.0.0.1:27017/harf
```

اضبط كذلك `SMTP_HOST` و`SMTP_PORT` و`SMTP_FROM`، وأضف `SMTP_USER` و`SMTP_PASSWORD` معًا إذا كان مزود البريد يتطلب مصادقة. عنوان الواجهة الافتراضي هو `http://localhost:5173` والخادم `http://127.0.0.1:4000`. يجب أن تتطابق قيمة `APP_ORIGIN` مع أحد الأصول المحددة في `CLIENT_ORIGINS`. لا تستخدم بيانات حقيقية أو كلمات مرور حقيقية عبر HTTP المحلي.

لإنشاء أول مشرف بعد اتصال قاعدة البيانات:

```powershell
npm run admin:create --workspace @harf/api
```

يشغّل الأمر تفاعليًا ويخفي إدخال كلمة المرور. لا تنشئ مشرفًا يدويًا بتعديل طلب HTTP أو بتغيير دور حساب من الواجهة.

### التحقق من التشغيل

- فحص حياة API: `GET http://127.0.0.1:4000/api/v1/health/live`
- فحص الجاهزية واتصال MongoDB: `GET http://127.0.0.1:4000/api/v1/health/ready`
- الاختبارات: `npm test`
- بناء الواجهة: `npm run build`

`live` يثبت أن عملية API تستجيب. `ready` يعيد HTTP 200 فقط عندما تكون قاعدة البيانات متصلة؛ انقطاعها يعطي HTTP 503 عمدًا.

## 5. كيف تنتقل الأخطاء عبر المنصة؟

1. يرسل المتصفح طلبًا عبر `apiRequest` في `apps/web/src/lib/api.js`.
2. يرسل العميل `Accept: application/json`، ويحافظ على Cookie باستخدام `credentials: include`. الطلبات المعدّلة للبيانات تضيف `X-CSRF-Token` إذا كان الرمز متاحًا.
3. يتحقق الخادم من الأصل وHTTPS عند لزومه، ثم يتحقق من صيغة الطلب والمصادقة والصلاحية وقواعد العمل.
4. أخطاء المسارات تمر إلى معالج الأخطاء المركزي في `apps/api/src/middleware/errors.js`.
5. يعيد الخادم JSON آمنًا، ويسجل تفاصيل مناسبة في سجل Pino. لا يرسل تفاصيل الاستثناء الداخلية أو المكدس للمتصفح.
6. يحول العميل استجابة HTTP غير الناجحة إلى خطأ JavaScript يحمل `status` ورسالة للمستخدم. واجهة العميل الحالية تعتمد على الرسالة والحالة؛ رمز الخطأ وتفاصيل الحقول موجودان في رد API ولا يحتفظ بهما كخصائص منفصلة على كائن الخطأ في العميل.

الشكل المعتاد لخطأ API:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid data.",
    "details": [
      { "path": "name", "message": "String must contain at least 2 character(s)" }
    ]
  }
}
```

`details` اختيارية، وتظهر في الأخطاء المعروفة عند توفر تفاصيل آمنة. الاستثناء غير المتوقع يرجع رسالة عامة مثل `An unexpected error occurred.`؛ ابحث عن سببها في سجل الخادم بدل كشف تفاصيل داخلية للمستخدم.

### رموز حالات شائعة

| HTTP | المعنى العام | ما يجب فحصه |
|---|---|---|
| 400 | طلب غير صالح، JSON معطوب، أو فشل تحقق | صيغة JSON والحقول المطلوبة؛ اقرأ `error.code` و`details` |
| 401 | لا توجد جلسة صالحة أو انتهت | تسجيل الدخول من جديد، وصلاحية Cookie |
| 403 | الأصل أو CSRF أو الصلاحية مرفوضة | `CLIENT_ORIGINS`، رمز CSRF، حالة الحساب والدور |
| 404 | المسار أو المورد غير موجود/غير متاح للمستخدم | المسار ومعرّف المورد وملكيته؛ بعض الموارد المخفية تعيد 404 لحماية الخصوصية |
| 413 | جسم الطلب أكبر من الحد | طلبات JSON محدودة إلى 32 KB؛ تحقق من أن الملف يرسل عبر مسار رفع مخصص |
| 429 | تجاوز حد الطلبات | انتظر انتهاء فترة التحديد، وافحص التكرار أو معدل الطلبات |
| 500 | خطأ داخلي غير متوقع | راجع سجل API المرتبط بالتوقيت والطلب، دون إعادة إرسال أسرار |
| 503 | قاعدة البيانات أو خدمة غير مهيأة/متاحة | افحص جاهزية MongoDB أو إعداد الخدمة المحددة |

## 6. تشخيص الأخطاء المتكررة

### أ. الصفحة تعمل لكن تسجيل الدخول أو البيانات تفشل

1. افتح `/api/v1/health/ready` على عنوان API.
2. إذا كانت الحالة 503 و`database` تساوي `disconnected`، تحقق من تشغيل MongoDB ومن `MONGODB_URI` وإمكانية الوصول إلى المضيف والمنفذ.
3. راجع سجل تشغيل API؛ لا تضع URI قاعدة البيانات أو بيانات الاتصال في رسالة عامة أو لقطة شاشة.
4. أعد تشغيل API بعد تعديل الإعدادات. في التطوير قد تبدأ العملية دون قاعدة بيانات، لكن مسارات البيانات ستظل غير متاحة حتى الاتصال.

### ب. رسالة المتصفح عن CORS أو ظهور 403

- تأكد أن عنوان الواجهة الفعلي يطابق أصلًا كاملًا في `CLIENT_ORIGINS`، بما في ذلك البروتوكول والمنفذ، وأن `APP_ORIGIN` ضمن القائمة.
- تحقق من `VITE_DEV_API_TARGET` إذا كان Vite لا يوجه `/api` إلى الخادم الصحيح.
- لا تستخدم `*` مع Cookies أو بيانات الاعتماد.
- قد يعرض المتصفح خطأ CORS عامًا ويخفي جسم الرد؛ افحص تبويب Network لمعرفة الطلب والحالة، ثم سجل الخادم.

### ج. `HTTPS_REQUIRED` أو خطأ Cookie في الإنتاج

- يجب أن تصل الطلبات إلى API عبر HTTPS في الإنتاج.
- إذا أنهى Proxy الاتصال المشفر أمام API، فراجع `TRUST_PROXY` واضبطه على عنوان/شبكة Proxy موثوقة أو إعداد مدروس يناسب البنية الفعلية.
- لا تستخدم `TRUST_PROXY=true` عشوائيًا. الثقة الخاطئة قد تجعل الخادم يسيء تفسير مصدر الاتصال أو البروتوكول.
- لا يحول Express طلب HTTP إلى HTTPS تلقائيًا؛ الرفض مقصود لتجنب حلقات التحويل وعدم الثقة في رؤوس Proxy غير الموثوقة.

### د. `INVALID_JSON` أو `REQUEST_TOO_LARGE`

- `INVALID_JSON` يعني أن جسم الطلب لا يحتوي JSON صالحًا؛ تحقق من علامات الاقتباس والفواصل و`Content-Type: application/json`.
- `REQUEST_TOO_LARGE` يعني تجاوز حد JSON البالغ 32 KB. لا تحاول تضمين ملف ثنائي داخل JSON؛ استخدم مسار الرفع المخصص والقيود التي يفرضها.

### هـ. `VALIDATION_ERROR`

- اقرأ `error.details` لتحديد اسم الحقل (`path`) ورسالة التحقق.
- أرسل الحقول المسموح بها فقط وبالنوع المتوقع؛ واجهات API تستخدم مخططات صارمة وقد ترفض الحقول الزائدة عمدًا.
- لا تعالج الأمر بإزالة التحقق من الخادم أو تجاوز مخطط الطلب.

### و. `CSRF` أو انتهاء الجلسة أو منع الوصول

- عند `401` سجّل الدخول مجددًا؛ قد تكون الجلسة انتهت أو أبطلت بعد تعليق الحساب أو تغيير حالة اعتماده.
- عند `403` تحقق من أن الطلب المعدّل للبيانات أرسل رمز CSRF المرتبط بالجلسة وأن `Origin` موثوق.
- تحقق أن الحساب متحقق من البريد ونشط ومعتمد، وأن المسار يناسب دوره.
- يجب أن تكون Cookies مفعلة للعنوان الصحيح. تستخدم الواجهة `credentials: include`؛ أما الإعداد الخاطئ للنطاق أو SameSite أو HTTPS فقد يمنع المتصفح من إرسال Cookie.

### ز. مشاكل البريد الإلكتروني

- تحقق من `SMTP_HOST` و`SMTP_PORT` و`SMTP_SECURE` و`SMTP_FROM`، ومن إعداد بيانات الدخول كزوج إذا استُخدمت.
- يجب أن تكون `SMTP_SECURE` إما `true` أو `false`. راجع متطلبات مزود SMTP والمنفذ والجدار الناري.
- إعدادات البريد غير المكتملة قد تجعل التحقق أو استعادة كلمة المرور غير متاحة. لا تضع كلمة مرور SMTP في سجلات أو صور شاشة.
- فشل إرسال البريد الاختياري لا يلغي الإشعار المحفوظ داخل المنصة؛ افحص سجل الخادم ومزود البريد.

### ح. `VIDEO_PROVIDER_NOT_CONFIGURED`

هذه ليست مشكلة اتصال عابرة: موفر الفيديو وبيانات اعتماده غير محددين في المشروع حاليًا. الخدمة ترفض إصدار بيانات دخول للفيديو عمدًا. لا تضع مفاتيح مزود الفيديو في متغيرات `VITE_*` أو في ملفات الواجهة؛ يتطلب تفعيلها اختيار موفر ومراجعة إعداداته وخصوصيته أولًا.

### ط. `NOT_FOUND` أو 404 مع مورد محدد

- تحقق من بادئة `/api/v1` واسم المسار ومعرّف المورد.
- يمكن أن تعني 404 أيضًا أن المورد غير موجود أو أن المستخدم لا يملك صلاحية الاطلاع عليه؛ هذا مقصود في بعض الموارد لحماية بيانات الأطفال.
- تحقق من تسجيل الدخول والملكية والدور بدل تجربة معرّفات أو حسابات لا تخصك.

## 7. السجلات ومعلومات الدعم

- سجل API يستخدم Pino؛ مستوى السجل يضبطه `LOG_LEVEL` (الافتراضي `info`).
- يسجل الخادم أخطاء 5xx، ويحذر عند رفض الطلبات المعروفة. لا يسجل معاملات URL في سجل HTTP، ويخفي بيانات اعتماد وCookies وحقولًا حساسة عند التسلسل.
- ابدأ بجمع: وقت الخطأ والمنطقة الزمنية، المسار دون بيانات شخصية، HTTP status، `error.code`، خطوات إعادة الإنتاج ببيانات اختبار، وحالة `health/ready`.
- لا ترسل كلمات مرور أو Cookies أو CSRF tokens أو روابط استعادة الحساب أو `MONGODB_URI` أو إيصالات الدفع أو بيانات الأطفال/ملاحظات الاستشارة في بلاغ الدعم.
- لا تكرر طلب دفع أو حجز موعد عدة مرات لمجرد ظهور خطأ في الواجهة؛ تحقق من سجل العملية أولًا لتجنب طلبات مكررة.
- عند إضافة معالجة جديدة: استخدم أخطاء المجال المعروفة ومخططات التحقق الموجودة، مرر الخطأ للـ middleware المركزي، أعد رسالة آمنة، وسجل الخطأ دون أسرار. لا تبتلع الاستثناء ولا ترجع نجاحًا وهميًا.

## 8. حدود حالية يجب معرفتها

- لا يوجد إعداد استضافة أو نطاق أو Proxy إنتاجي مُختار في المستودع.
- يحتاج النظام قبل استقبال بيانات حقيقية إلى سياسة احتفاظ وحذف وموافقة قانونية ملائمة لبيانات الأطفال، وخطة نسخ احتياطي واستعادة ومراقبة.
- التحقق من الدفع يدوي، ولا يوجد تكامل دفع آلي.
- موفر الفيديو غير مختار وغير مفعّل.
- التقارير التعليمية المرتبطة بالجلسات متاحة وفق الموافقات، لكن تقارير تقدم الألعاب المنشأة تلقائيًا غير منفذة.
- حدود معدل المصادقة في الذاكرة؛ التشغيل متعدد النسخ يحتاج مخزنًا مشتركًا قبل الاعتماد على هذه الحدود.
- ملفات الوسائط خاصة وخارج مجلد الويب؛ يجب حفظ نسخ احتياطية متوافقة مع بياناتها الوصفية في MongoDB.
